# AQD V2 backlog — Complete product vision

Updated October 5, 2026. V2 contains **the complete connected AQD product and all previously planned enhancements**. The former connected V1 is now the V2 core; the new [V1](v1-release.md) is a private device-only closet/planner MVP. This is product/architecture/Paper preparation, not an implementation commitment, provisioned service or claim of runtime readiness.

## Phase handoff

Preserve V1 local records, photos, stable IDs and archives. V2 extends V1 without replacing its private UI/features or resetting data. V1 already has Home/Closet/Planner/Agent/local Profile/Settings, themes/plans/routines/trips/packing, local history/insights and Agent recovery. V2 adds cloud association only through explicit account/destination/data review; failure keeps the local closet recoverable. Signing in or syncing never publishes anything. A user can keep private local work while choosing whether to join connected AQD.

The complete vision retains **Home · Closet · Planner · Agent · Profile** (five equal-width icon-only native slots with destination accessibility names, full hit areas ≥44 × 44 pt), with human Inbox through a persistent labelled 44-point V2-only root-toolbar entry → I01 → conversations, not a tab, private Today plus All/Following feeds, shared manual/assisted capabilities, curated public snapshots and human messaging. V2 needs the [complete architecture](../architecture/v2.md), [connected core acceptance](v2-release.md) and [prepared design requirements](../design/v2-requirements.md). V1 implementation must not inherit these service dependencies.

## Private fit journal and explicit sharing

Carry forward V1's [private dated fit journal](../features/profile-account.md#v1-private-fit-journal), including local data/media, stable dates, minimal outfit snapshots, draft protection and export/restore. A fit memory remains distinct from plans and actual wear; sharing cannot increment wear or rewrite its history. Keep private journaling available without connected opt-in and keep Style/wear insights reachable.

V2-C07/C08 add an explicit publication action for a selected memory: review the exact selected photo rendition or honest outfit composition, audience and public content before publishing through connected identity/media/safety gates. Never upload/publish the original or whole journal implicitly. Private notes are excluded, not prefilled into public copy; the user must deliberately enter any public caption. Saving/editing/linking a fit, signing in, syncing or changing defaults never posts it automatically. Private defaults remain private; cancelling/failing publication preserves the journal and draft without false success. Review/update/unpublish governs the separate public snapshot, not the private memory's lifecycle.

Acceptance: publish only the reviewed selected rendition/composition; verify private notes and unselected originals/memories are absent from public payloads and surfaces. Test cancellation/failure/retry, unavailable media, access revocation and no automatic posting after save/edit/sync; wear counts remain unchanged. This is new approved spec/design scope only; native publishing and services remain unimplemented/unverified.

## Infrastructure and cost reality

Start V2 with one modular trusted backend, PostgreSQL, authorized object storage and durable DB jobs plus a bounded worker. Add realtime hints, auth email, protected admin/monitoring/moderation and tested backup/restore. Push, external APIs, billing verification, catalog/media/calls and other clients add infrastructure when their extension is chosen. Supabase/Cloudflare remain proposals; CloudKit private sync alone does not supply cross-platform social, moderation or human Inbox.

The old [cost snapshot](../architecture/costs.md) applies to connected V2 assumptions, not V1 spending. Refresh provider pricing/limits, region, taxes, media/egress, email, AI retries, monitoring and operating labor before launch. Zero starting users does not eliminate baseline or moderation costs. No purchases or cloud configuration are authorized by this branch.

## Implementation and release considerations

Deliver the complete V1 local app and measure real usage first. Then prioritize additive V2 increments; every requirement remains retained regardless of delivery order. For V2, settle identity/association/sync/retention/media/moderation/messaging and operations before exposing connected actions. Verify access with owner, second account, guest and blocked participant; validate unknown/retried outcomes and actual backup restore. Capability-dependent extensions need real device/provider measurements, content rights, privacy/consent and an approved operating budget.

All backlog rows have a requirement/design reference; core rows have existing detailed canonical screens. Extension boards prepare entry, consent, preview/result and recovery requirements without selecting providers or promising every extension in one launch. [Design coverage](../design/v2-coverage.md), [V2 design requirements](../design/v2-requirements.md), [implementation plan](../delivery/implementation-plan.md) and [verification](../delivery/verification.md) distinguish preparation from delivered evidence.

V1’s [local photo capture/editor](../design/capture-photo.md) is retained in V2: photo needed for new-piece save, manual classification and missing-photo draft recovery, portrait presentation, full-image Fit, crop/rotate/reset and original retention. V2-E01 adds advanced processing/imports around that same review flow. Sync must preserve edit recipes/revisions; publication reviews the chosen rendition and never publishes the original implicitly.

### Explicit Agent provider option

Owner-approved V2 direction: retain the Agent tab on unsupported iPhones and offer a selected LLM provider when that integration ships. [Agent availability and provider selection](../features/agent.md#agent-availability-and-provider-selection) owns first-request context/privacy/cost disclosure, consent, provider provenance and offline/quota/failure recovery. This extends V2-C03; no provider/service is provisioned, no release date promised and no automatic cloud failover is permitted.
