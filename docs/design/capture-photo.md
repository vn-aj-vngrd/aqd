# Piece photo capture and editing

October 6, 2026. Shared by the complete local V1 and additive V2. [Wardrobe](../features/wardrobe.md) owns record validation and persistence. Paper remains the visual source. This is a prepared design and implementation contract, not working native functionality.

## Flow and references

| State | Paper reference | Behavior |
| --- | --- | --- |
| New draft, no photo | V1 L04 | Compact full-width Add photo control opens L159's native photo-source sheet; no separate Take photo action or empty portrait preview. Name/category start empty. Save disabled until an accepted, locally prepared photo, name and category are valid. |
| Initial source options | V1 L159 | Add photo opens a native bottom sheet on iPhone, adaptive popover on wider layouts. Choose from Photos → system PhotosPicker; Take photo → native camera. Close/outside-tap/swipe dismiss without changing the draft. No Remove action before a photo exists. |
| Selected photo | V1 L75; V2 W27 | Full image fitted into a portrait preview. Edit photo opens the editor; Change opens native photo options. Save creates the piece only after local persistence succeeds. |
| Landscape photo | V1 L76 | Same portrait viewport, with neutral padding above/below; no stretching or automatic crop. |
| Edit photo | V1 L77; V2 W31 | Optional 3:4 crop, move/zoom, Rotate, Reset and Fit entire photo. Cancel keeps the previous selection; Use photo applies edits to the draft only. |

| Photo missing | V1 L79 | Name/category retained after removal or a missing-photo validation attempt. Inline “Add a photo to save this piece.” Save stays disabled; the same compact Add photo row opens L159 to recover the draft, without a portrait placeholder or separate camera action. |

Change → L78 → replacement, capture or removal. Missing-photo validation → L79 → Add photo → L159 → Photos/camera → L75/L76. Valid selected-photo save → L05. Failed saves stay in the draft. L43/L44 readiness derives from actual saved categories, including existing legacy records with unavailable media; these remain readable. V2 W06/W07/W27/W31 share the same media behavior and local draft protection; identity, sync and community do not gate editing.

## Composition

L04's approved no-photo state uses Photo → a full-width 350 × 88-point opaque surface control with 12-point corners, 20-point padding, photo symbol, Add photo label and disclosure chevron, with a 12-point label/control gap. Remove the separate Take photo action. The entire row opens L159's native source sheet; expose one accessible Add photo button with no-photo state and keep symbols decorative. The sheet offers Choose from Photos and Take photo as 56-point reference rows in one opaque group, plus a 44-point Close control, native drag indicator and safe-area handling. Use OS-owned sheet/popover geometry and adaptive detents in implementation rather than recreating the static 304-point drawing. Move accessibility focus into the sheet, hide the background from focus, and return focus to Add photo after dismissal; source selection dismisses the sheet before presenting the system picker/camera. No portrait well or redundant “No photo selected” copy appears before acceptance. Name/Category follow; Save stays bottom-aligned with a 64-point screen-bottom clearance in the 390 × 844 base reference, leaving approximately 50 points above the home indicator. L04/L75/L76/L79 and V2 W27/W07 plus their connected capture/recovery copies share the final Save edge; selected-photo stacks use tighter 8-point group gaps without shrinking the Fit preview or 50-point action. Native implementation uses safe-area/keyboard insets and scrollable content, not a universal hard-coded 64-point device inset; Dynamic Type adaptation remains required. L79 now reuses L04's exact compact selector, retaining entered name/category and red missing-photo validation above bottom-aligned disabled Save. Connected first-capture/recovery review copies now reuse the accepted source-sheet-over-draft and portrait Fit/editor structure; capture More details applies through shared L94/L95 to the parent draft only. Saved-record W09/W21 editors retain Save changes.

For accepted media, use one 3:4 portrait presentation viewport, 168 × 224 points in the base capture reference, with 4-point photographic corners, opaque neutral ground and no decorative outline or shadow. Preserve aspect ratio. The source may be portrait, square, landscape, panoramic or already rotated: normalize orientation and fit the complete image by default. Neutral padding belongs to presentation, not the original image. Never apply a crop just because the destination has portrait proportions.

Keep one vertical flow: Photo header → preview → one Edit photo action → labelled fields → Save. Change remains a separate header action. The approved L04 no-photo layout uses the compact Add photo control above; source actions live only in L159's sheet. Empty placeholders must not resemble a selected image or a loading failure. Photo menus use native functional chrome; ordinary preview/form surfaces remain flat. Native hit areas are at least 44 points. Save uses the shared 50-point primary; action stacks retain Welcome's 12-point gap.

The editor has a larger 240 × 320 portrait crop viewport, grid only while adjusting, Fit entire photo / Portrait 3:4 framing choices, Rotate, Reset, a labelled Zoom control and Use photo. Fit preserves every pixel of the source in the presentation. Portrait cropping is an explicit user choice; constrain the crop to source bounds. Rotate turns 90 degrees; Reset restores original orientation and Fit. Keep the whole garment visible unless the user deliberately chooses otherwise. The sample photos are existing authorized reference fixtures, not new production assets.

## Draft, import and recovery states

- Every new piece needs an accepted, locally prepared photo plus a valid name/category before Save enables. Visible labels are simply Photo, Name and Category; never append Required or Optional. Choosing a photo does not fabricate either field. Manual classification remains available without AI. Classifier proposals remain separately marked and editable.
- During local preparation or an iCloud-backed picker transfer, show one system progress indicator and Cancel; retain fields and the previously accepted image. Do not show an empty placeholder as progress. Ignore late results from cancelled/replaced requests.
- Picker/camera cancellation leaves the draft intact. Camera denial offers Choose photo, Settings where applicable, or Keep draft. Metadata entry remains available, but cannot save a new piece without a photo. User-selected iCloud media may need network access; this does not introduce an AQD backend dependency.
- Unreadable, unsupported, oversized or failed media shows a local inline error with Try again / Choose another / Keep draft. Preserve fields and previous accepted media. Failed editor rendering keeps the previous accepted rendition and crop settings.
- Change commits the replacement only after decoding/preparation succeeds. Remove clears draft media and edits without deleting the source Photos asset, retains fields and disables Save until another photo is accepted. Cancel in the editor discards only uncommitted editor changes.
- Use photo confirms framing, not a saved piece. Save still validates and persists atomically; failure retains the original, edit parameters and prepared rendition. Restart restores the recoverable draft; clean abandoned staging safely.

## Apple APIs and implementation boundary

Use [PhotosPicker](https://developer.apple.com/documentation/photosui/photospicker) / PHPicker for user-selected library media and native camera capture. Apple offers basic editing through [UIImagePickerController.allowsEditing](https://developer.apple.com/documentation/uikit/uiimagepickercontroller/allowsediting); this is not a commitment to the AQD editor's exact 3:4 controls or to embedding the full Photos app editor. Implement the prepared framing UI with native SwiftUI/UIKit controls and local [Core Image cropping](https://developer.apple.com/documentation/coreimage/ciimage/cropped(to:)) or Core Graphics. API choice, orientation handling and gesture/accessibility behavior require a prototype on supported devices. No Apple Intelligence or server is required for deterministic crop/rotation.

Preserve an app-private, metadata-minimized original plus normalized crop/rotation parameters and a derived thumbnail/rendition. Do not modify the user's Photos-library source. Normalize EXIF orientation before interpreting pixel coordinates; decode/downsample within measured memory limits and preserve useful color information. Stage media before updating record references. Export/restore includes the referenced source, edit metadata and derivatives required for recovery; local erase clears all AQD-owned copies. Existing protection and backup-exclusion rules apply. V2 sync must preserve the edit recipe/revision; publication reviews the exact rendition and does not expose the original automatically.

## Native acceptance

Test portrait, landscape, square and extreme aspect ratios; orientation metadata; low-resolution and large HEIC/JPEG sources; Fit versus explicit crop; reset/rotate/cancel/reopen; replacement/removal after edits; late/cancelled imports and photo preparation failure. A landscape shoe must remain fully visible in Fit. A new piece without a photo cannot save, even with valid name/category. Check removal, denied/cancelled/failed imports and attempted validation; fields stay intact and no receipt/readiness update occurs. Existing records with lost media keep a category placeholder and remain manageable; this requirement does not delete or corrupt legacy data. Verify draft recovery, export/restore and media cleanup without losing the prior saved image.

Support scrollable forms and keyboard-safe Save placement on smaller devices and larger text. Dynamic Type grows labels/controls without shrinking hit areas. VoiceOver exposes selected framing, adjustable zoom and accessible reposition actions; gestures have button/accessibility alternatives. Crop grid is decorative. Reduce Motion updates immediately; dark and Increased Contrast use semantic surfaces and boundaries. Physical-device behavior and memory limits remain unverified on this planning branch.
